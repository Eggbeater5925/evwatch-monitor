## 0. 结论

这是个**明文 PHP 后端**，接口比麦希充简单，但能力更全：

| 能力 | 荟铭 | 麦希充 |
|---|---|---|
| 查在不在充 | `hasUsingOrder` 一个字段 `has` | `getUsingOrderList` 列表 |
| 实时功率 | ✅ `charging_w`（实测 790W） | ⚠️ 没插车时恒 0 |
| 已充电量 | ✅ `electrics`（实测 0.145 度） | ❌ 结束单也是 0 |
| 远程结束 | ✅ `closeCharge` | ✅ `stopOrder` |
| 开始充电 | ✅ `makeOrder`（但本项目不做） | ❌ 要微信支付分确认 |
| 结束原因 | ❌ 只有状态码 131/666 | ✅ 28 条字典 |
| token | UUID，无 exp，无登录接口 | JWT，7 天，手机号直换 |

所以这个数据源的判满**主要靠功率**（有真实数据），不需要像麦希充那样只靠时长兜底。

## 2. 认证：一个 UUID token，放在表单体里

所有业务接口都是 `POST` + `application/x-www-form-urlencoded`，token 作为普通参数：

```
POST /vv/order/api/index/details
content-type: application/x-www-form-urlencoded
appid: wx9e8dc02a60df8d1f

order_id=<order_id>&ctime=<ctime>&token=<token>
```

| 项 | 值 |
|---|---|
| 形态 | UUID v4，36 字符（`xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`） |
| 位置 | 表单体里的 `token` 参数（**不是** Header） |
| 有效期 | **没有 exp 可解**，UUID 本身不带时间；实测 1.9 天后仍有效 |
| 来源 | `POST /vv/usercenter/api/user/profile` 的 `data.userinfo.token` |
| 续期 | **抓包里没有登录接口**（无 `sendCode` / `login`），只能重新抓包 |

> 和麦希充不同：这不是 JWT，解不出到期时间，也不能用手机号直换。
> 代码里只记录 `obtained_at`，用来显示「已经用了几天」，不做过期判断。

## 3. 接口清单（8 个）

| 接口 | 参数 | 返回 | 本工具用? |
|---|---|---|---|
| `POST /vv/usercenter/api/user/profile` | token | `userinfo`（含 token、余额、手机号）+ `thirdinfo`（openid） | ✅ 验 token |
| `POST /vv/order/api/index/hasUsingOrder` | token [macno] | `has: 0/1` + `info{order_id, ctime, using_time}` | ✅ 判断在不在充 |
| `POST /vv/order/api/index/details` | order_id + ctime + token | 订单全字段：功率、电量、金额、状态 | ✅ 核心 |
| `POST /vv/order/api/index/closeCharge` | order_id + token | `{code:1, msg:"结束充电成功"}` | ✅ 自动停 |
| `POST /vv/order/api/index/getOrderList` | page + pagesize + status + token | `list[]`（订单摘要） | ✅ 找最近一单 |
| `POST /vv/device/api/index/getDeviceInfo` | macno + token | 设备 + `socket[]` 插座列表 | 调试 |
| `POST /vv/device/api/index/getSocketInfo` | macno + socket_id + token | 插座 + 电价 | 调试 |
| `POST /vv/device/api/index/index` | lng + lat + page + pagesize + token | 附近站点（2290 个） | 未用 |

`POST /api/common/config`（key=site.tel）只返回客服电话和版权声明，不涉及业务。

### 3.1 成功码是 `code == 1`

和麦希充（`code == 0`）相反。这是接入时最容易踩的坑：

```json
{"code": 1, "msg": "success", "data": {...}}      // 成功
```

代码里统一在 `huiming._post()` 判断，调用方不用管。

## 4. 字段：一单长什么样

`details` 的 `data`（节选，值已脱敏）：

```json
{
  "id": 10000001,
  "number": "2026xxxxxxxxxxxxxxxx",
  "macno": "8300000000XXXXXX",
  "status": 131,
  "start_time": 1700000000,
  "finish_time": 0,
  "hour": 1,
  "use_times": 660,
  "charging_w": "790.31",
  "electrics": "0.14489",
  "orders_money": "0.00",
  "realprice": "0.00",
  "temp_money": "0.00",
  "is_abnormal": 0,
  "title": "XX步行街",
  "address": "XX步行街",
  "socket_number": 9,
  "elec_price": {
    "elec_fee": "0.69",
    "service_fee": "0",
    "power": [
      {"min": "0",   "max": "130",  "price": "0.45"},
      {"min": "130", "max": "200",  "price": "0.5"},
      {"min": "200", "max": "300",  "price": "0.55"},
      {"min": "300", "max": "400",  "price": "0.65"},
      {"min": "400", "max": "500",  "price": "0.75"},
      {"min": "500", "max": "600",  "price": "0.85"},
      {"min": "600", "max": "800",  "price": "1.2"},
      {"min": "800", "max": "1000", "price": "1.5"}
    ]
  }
}
```

| 字段 | 含义 | 可靠性 |
|---|---|---|
| `status` | `131` 充电中 / `666` 已结束 | ✅ 实测两单 |
| `charging_w` | **实时功率（W）** | ✅ 实测 790W，随车变化 |
| `electrics` | 已充电量（度） | ✅ 实测 0.145 |
| `use_times` | 已用时长（秒） | ✅ 与 `start_time` 差吻合 |
| `orders_money` | 订单金额 | ⚠️ **充电中一直是 0.00**，结束后才结算 |
| `hour` | 购买时长（小时） | ✅ |
| `finish_time` | 结束时间，未结束为 `0` | ✅ |
| `is_abnormal` | 异常标记（0 正常） | 未验证 |
| `temp_money` | 预付金额 | 实测 0 |

**关键差异**：`orders_money` 在充电中不累加（麦希充会从 1.00 涨到 4.26），
所以「已花多少钱」只能等结束后看。进度推送里金额显示 ¥0.00 是正常的。

### 4.1 状态码

| 值 | 含义 | 依据 |
|---|---|---|
| `131` | 充电中 | `finish_time == 0`，`hasUsingOrder.has == 1` |
| `666` | 已结束 | `finish_time` 有值 |

抓包里没有第三种状态，也没有「结束原因」。想区分「充满」和「主动结束」，只能靠自己的判据。

## 5. 计费模型

`elec_fee = 0.69` 元/度，服务费按实时功率 8 档（0.45 ~ 1.5 元/度）：

| 功率区间 | 服务费（元/度） | 综合单价 |
|---|---|---|
| 0–130W | 0.45 | 1.14 |
| 130–200W | 0.50 | 1.19 |
| 200–300W | 0.55 | 1.24 |
| 300–400W | 0.65 | 1.34 |
| 400–500W | 0.75 | 1.44 |
| 500–600W | 0.85 | 1.54 |
| 600–800W | 1.20 | 1.89 |
| 800–1000W | 1.50 | 2.19 |

**功率越高，服务费越贵**，和麦希充是同一个定价思路（限制大功率车长时间占位）。
实测那单 790W 落在 600–800 档，综合约 **1.89 元/度**。

## 6. 怎么判「在充电」

### 6.1 状态机

```
hasUsingOrder.has == 0 且没单        → 空闲
hasUsingOrder.has == 1               → 在充，拿 info.order_id 查 details
details.status == 131 且 finish_time == 0 → 充电中
details.status == 666                → 已结束
```

### 6.2 判满四档

| 优先级 | 判据 | 说明 |
|---|---|---|
| 1 | **SOC ≥ `--soc-target`（默认 90）** | 优先读 `battery.csv` 的真实 SOC；读不到才用容量/功率估算 |
| 2 | **降压**：功率 ≤ 峰值 × `--droop-ratio`（默认 0.9）持续 `--droop-hold`（默认 2 分钟） | 进入恒压尾声，后面的电又慢又不值 |
| 3 | 功率「有载 → 空载」持续 `--full-minutes`（默认 10） | 拔车/桩停 |
| 4 | **购买时长剩 `--stop-before-end`（默认 60 秒）** | 把买的时段用满，不为最后几个百分点续费 |

> 实测功率 819~826W 会小幅波动，降 10% 才认，不会误触发。
> 策略细节与费用测算见 [荟铭-充电策略.md](荟铭-充电策略.md)。

判满后调 `closeCharge`，3 秒后复查 `details.status == 666`。

**为什么必须先见过有载**：没插车时 `charging_w` 就是 0，直接按「0W = 充满」会在你还没插上时把单停掉。这和麦希充那次教训一样。

### 6.3 与麦希充的判满差异

| | 荟铭 | 麦希充 |
|---|---|---|
| 功率数据 | 真实（790W） | 没插车时 0，有载未验证 |
| 电量数据 | 真实（0.145 度） | 结束单也是 0 |
| 桩报充满 | 无 | `endType ∈ {06,15,30,31}` |
| 主要判据 | **功率掉下来** | 桩报 + 时长兜底 |

## 7. 安全发现

> 以下只做静态观察，**没有做任何越权测试**。

| 级别 | 问题 |
|---|---|
| P1 | `details` 只需要 `order_id` + `ctime`，且 `ctime` 传 `undefined` 也能成功 —— 提示服务端可能不校验这两个值的归属。**未验证**，不做越权尝试。 |
| P1 | `profile` 返回 `openid` / `unionid` / 手机号 / 余额，字段明显超出前端所需。 |
| P2 | token 走 POST body，虽然比 query 好，但仍会被 PHP access log / 反代日志记录。 |
| P2 | `X-Powered-By: PHP/7.1.33`，该版本 2019 年已停止支持。 |
| P2 | `Access-Control-Allow-Origin: *`，配合 body 里的 token，理论上任意网页都能构造请求（仍需拿到 token）。 |
| P3 | `getOrderList` 的 `pagesize` 没有看到上限（抓包里传过 `999999999`）。 |

本项目只读自己的数据；`closeCharge` 也只对 `hasUsingOrder` 返回的本人订单调用。

## 8. 怎么用

```bash
# 1) 抓包拿 token：profile 响应里的 data.userinfo.token
python3 evwatch/huiming_watch.py settoken "<token>"

# 2) 看一眼
python3 evwatch/huiming_watch.py ping
python3 evwatch/huiming_watch.py status
python3 evwatch/huiming_watch.py sim          # 离线演示判满，不联网

# 3) 常驻
bash deploy/install.sh --huiming
```

| 命令 | 作用 |
|---|---|
| `ping` | 验 token + 账号 + 在不在充 + 最近 3 单 |
| `status` | 当前这一单的完整状态 |
| `once` | 一份快照 |
| `orders` | 订单列表 |
| `watch` | 监听 + 判满 + 自动停 |
| `sim` | 离线演示判满过程 |
| `settoken` | 写入并验证 token |
| `stop --confirm` | 手动结束当前订单（不加 `--confirm` 只试运行） |

## 9. 风险与合规

1. **仅限本人账号、本人订单。** 本项目不含下单、充值、退款功能，也不做越权查询。
2. 协议信息来自对公开客户端（微信小程序）的抓包分析，用于个人自动化；小程序著作权归深圳市荟铭科技有限公司。
3. 接口随时可能变；`closeCharge` 是写操作，只在判满时调用一次，失败会推送告警而不是重试。
4. token 是 UUID、没有过期时间，一旦泄露等于账号被接管 —— **不要提交 `huiming.json`**（已在 `.gitignore`）。
