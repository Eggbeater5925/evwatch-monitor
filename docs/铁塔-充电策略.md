# 铁塔充电桩：收费标准与「什么时候掐掉」策略

> 数据来源：2026-10-23 一整单实盘（19:47:47 → 21:21:40，1 小时 33 分，2.58 元，SOC 50% → 100%）
> + 扫码接口返回的费率模板 + 小程序「收费标准」页截图。接口细节见 [小哈智电-接口分析.md](小哈智电-接口分析.md) §11。

## 0. 一句话结论

**桩的「充满自停」判得晚，服务费按小时收且比电费贵** —— 所以不能等桩，
要以**电池 BMS 报停**为准主动结束；在此基础上再用「下一小时还值不值」做第二道闸。

## 1. 收费标准（实测）

这个站（深圳，价费分离模板 id 1111）的两笔钱是**分开算**的：

| 项 | 单价 | 说明 |
|---|---|---|
| 电费 | **0.69 元/度** | 全天平段，按实际充入度数 |
| 服务费 | **按功率档位计，单位是「元/小时」** | 见下表；**不是按度** |

| 功率档 | 服务费（元/小时） |
|---|---|
| 0–100W | 0.45 |
| 100–200W | 0.50 |
| 200–300W | 0.55 |
| 300–500W | 0.60 |
| 500–800W | 0.65 |
| 800–1000W | 0.80 |
| 1000–1200W | 1.00 |
| ≥1200W | 1.20 |

**核算验证**（这就是为什么可以相信这张表）：

```
功率 1.19kW → 落在 1000–1200W 档 → 服务费 1.00 元/时
电费 = 0.69 × 1.19 = 0.82 元/时
合计 1.82 元/时
实测账单速率 0.03 元/分 = 1.80 元/时        → 误差 1.2%
```

服务费占 **55%**，确实比电费（0.82 元/时）还贵。**这就是「末端不划算」的根源**：
小电池到末端只进几个点，服务费照付。

## 2. 是「按分钟」还是「不满一小时按一小时」？

**这个站是按分钟实时结算的**，跨整点不会被多收一整段。三条证据：

| 证据 | 数据 |
|---|---|
| 60 分钟整点没有跳变 | 59 分 = 1.60 元、**61 分 = 1.60 元**、63 分 = 1.75 元 |
| 全程没有大额跳变 | 单次增量最大 0.16 元，**没有 >0.30 元的跳变**（整段计费会一次性跳一整段） |
| 模板粒度 | `newCostTemplate.costMinute = "2"`（2 分钟结算粒度） |

但**不是所有铁塔桩都这样**：有的站按 30 / 60 分钟整段收费。两种桩的最优策略相反：

- **实时计费**：每分钟都在花钱 → 随时按「元/%」判断
- **整段计费**：段内已经付过钱，**继续充是免费的** → 段内别停，只在临近边界时算跨段账

程序会从 `costMoney` 的跳变模式自动识别（长时间不动 + 在 30/60 分钟处一次性跳一整段），
也可以用 `--billing-unit 30|60` 手动指定。

## 3. 判据体系（从硬到软，任一条成立就结束）

```
① 电池报停         chargeStatus 1 → 0/-1，连续 2 次
② 满电浮充         SOC 100% 且电池侧电流 ≤0.5A，连续 2 次
③ 价值判停         SOC ≥95% 且（下一小时预计涨不到 2 个点 或 每 1% 要花 >0.15 元）
④ 目标电量         达到 --target-soc 就停（默认关闭）
⑤ 桩侧兜底         电池数据拿不到时，桩侧电流跌到峰值 25% 以下连续 2 次
```

**防误杀的四道保险**

1. 开充 3 分钟内不判（`--warmup-min`）
2. ① 必须先见到过「充电中」，否则刚插上时 `chargeStatus=0` 会误判
3. 同一单连续 N 次才动（`--confirm 2`）；但**「已经停了」这个方向**只要缓存不超过 3 分钟，
   连着两次报停就算数（原先要求 `reportTime` 前进，实测多等 2 分 11 秒、白付 0.11 元）
4. **冷启动兜底**：服务重启 / 断网很久后恢复时，进程内存里的「见过充电中」已经丢了。
   此时若电池报「未充电/断电」且电量 ≥`--cold-soc`（默认 98%），照样判停 ——
   否则会永远判不了，一直充到桩自己停

## 4. 参数速查

| 参数 | 默认 | 作用 |
|---|---|---|
| `--confirm` | 2 | 连续几次才认定「电池停了」 |
| `--warmup-min` | 3 | 开充后多少分钟内不判 |
| `--full-current` | 0.5 | SOC 100% 时电流低于此值算停充（浮充） |
| `--cold-soc` | 98 | 冷启动兜底的电量门槛 |
| `--target-soc` | 0（关） | 充到该 SOC 就停，用于「够用就停」 |
| `--no-smart-stop` | 开 | 关掉价值判停 |
| `--min-soc` | 95 | 价值判停的电量下限（低于它绝不停） |
| `--min-gain` | 2 | 下一段预计涨幅低于此值就不值 |
| `--max-per-pct` | 0.15 | 每 1% SOC 花超过这个钱就不值（中段实测 0.03–0.07） |
| `--lookahead-min` | 60 | 往后看多久估值 |
| `--billing-unit` | 0（自动） | 30 / 60 = 手动指定整段计费 |
| `--pre-stop` | 5 | 整段计费时，离边界几分钟内才判跨段 |
| `--no-open-door` | 开 | 结束时不开仓门（可能产生占位费，默认开） |

## 5. 那一单的完整时间线（2026-10-23）

```
19:47:47  开充（充满自停，预扣 60.50 元）
19:48:43  发现充电，桩 1.19kW / 5.37A / 220V
19:49–21:14  SOC 50% → 98%，桩功率 1.19kW 稳定；已扣 0 → 2.47 元
21:17:17  电池 SOC 100%，但 chargeStatus 仍是 1、电流 10.18A（均衡阶段）
21:19:29  电池首次报 chargeStatus=0 / 0.0A   ← 其实这时就可以走了
21:21:39  第二份新报告到达 → 连续 2 次成立
21:21:40  调 endCharge → 返回 {"costMoney": 2.58, "returnFlag": false}
21:21:4x  复查：订单已消失 / endType 有值 → 已确认停止 → 推送（钉钉）
```

**结算**：93 分钟、2.58 元、SOC 50→100%，折算 ≈1.5 元/度，与「1.2kW 时 1.52 元/度」吻合。

**这段里两个已知损耗**：

| 环节 | 时间 | 代价 | 现状 |
|---|---|---|---|
| 100% 后均衡（status 仍=1） | 21:17→21:19，约 2 分 | 约 ¥0.06 | 设计如此（等 BMS 自己报停） |
| 等第二份新报告 | 21:19:29→21:21:40，2 分 11 秒 | 约 ¥0.11 | **已修**：缓存 ≤3 分钟且连续两次报停就算数 |

## 6. 三个反直觉的点

**① 服务费按功率档、单位是「元/小时」，所以「每度总价 = 0.69 + 服务费 ÷ 功率(kW)」**

同一档内，功率越接近上限越便宜；跨档那一瞬间会突然变贵：

| 功率 | 服务费 | 每度总价 |
|---|---|---|
| 999W | 0.80/时 | **1.49 元/度** ← 甜点 |
| 1000W | 1.00/时 | 1.69 元/度（跳 +13%） |
| 1199W | 1.00/时 | **1.52 元/度** |
| 1200W | 1.20/时 | 1.69 元/度（跳 +11%） |

小电池峰值约 1.2kW，**贴着 1199W 跑就是它能拿到的最优**；
想再省 2% 要压到 ≤999W，一趟 3 度电只省约 1 毛，不值得为此限流。

**② 末端降功率反而更贵**

| 功率 | 服务费 | 每度总价 |
|---|---|---|
| 1190W | 1.00/时 | 1.53 元/度 |
| 600W | 0.65/时 | 1.77 元/度（+16%） |

所以「功率掉下去 = 快满了 = 快能省钱了」这个直觉是错的：**掉功率的时候每度更贵，而且充得还慢**。
价值判停就是在这时候起作用的（实测末端 0.3–0.5 元/%，中段只要 0.05）。

**③ 桩侧三个「看起来有、其实没有」的字段**

| 字段 | 实测 | 含义 |
|---|---|---|
| `isReadCurrent` | `false` | 桩不上报实时电流，`current` 是 `power/220` 换算的；小程序会把「实时电流」那行隐藏，但「实时功率」照常显示 |
| `isDisplayDegree` | `false` | 桩不上报度数，`chargingDegree` 恒为 0，别当 0 度电 |
| `plugNum` 前缀 | 实测 `DTMF…`，抓包里是 `HBLF…` | 别按前缀做任何判断 |

## 7. 命令

```bash
# 看一眼：在充吗、充到哪、桩功率多少
python3 evwatch/tower.py status

# 离线看判定过程（不联网、不需要登录态）
python3 evwatch/tower.py sim

# 先只判不停，观察一单
python3 evwatch/tower.py watch --dry-run --no-push

# 正式跑
python3 evwatch/tower.py watch

# 只充到 90% 就停（够用就停）
python3 evwatch/tower.py watch --target-soc 90

# 桩是按 30 分钟整段收费的站
python3 evwatch/tower.py watch --billing-unit 30

# 人工立刻结束当前这单
python3 evwatch/tower.py stop
```

## 8. 还没验证 / 已知局限

- **整段计费**（30/60 分钟）只有离线用例覆盖，还没有真实站点跑过；自动识别需要先跨过一个边界才有数据。
- **换电柜式桩**：如果同一个桩/柜里还可能给别的电池充电，只看 BMS 的 `chargeStatus=0` 可能会停错单——
  这也是判据 ② 要求「电流也接近 0」的原因。目前这个站是单插口交流桩，不存在该问题。
- **开仓门**：默认 `openDoor=1`。客户端提示「不打开仓门将按时间收取费用」，所以开门是为了止损；
  代价是仓门整夜敞开、电池在公共站点有被拿走的可能。不想开就 `--no-open-door`。
- **计费上限**：模板里 `maximumConsumption = 15.00` 度，本场景远远用不到。
