## 2. 登录链路（明文）

```
559  POST api?user.account.wechatIdCheck   wx.login code → 是否老用户
566  POST api?user.account.weixinEasyLogin ← 一键登录
     ← {unionid, ticket, token, key, guid, userNewId, openId, mobile}
697  POST api?user.account.weixinMobileLogin（前置 690 发短信验证码）
     ← {ticket, token, key, guid, userNewId, mobile}
698  POST api?wechat.mp.sessionV2          ← {openId, unionid}
```

凭证含义：

- `token`：32 位 hex，会话令牌（业务接口靠它识别用户）。
- `ticket`：`base64(userId) + "." + base64(32 字节签名)`，例 `MTgwMDAwMDAwMg==.xxx` → userId `1000000005`。
- `key`：16 字节 base64。**与报文加密无关**（实测排除），应是该账号的本地数据密钥。
- `guid`：设备指纹。

> ⚠️ 这份抓包含**两个账号**（`13800138001` / `13800138002`）。`token`+`ticket` 等同密码。

## 3. 电池接口（已解出真实字段）

### 3.1 `swp.li.user.battery.list` — 拿 batteryNo

```json
// 请求
{"systemCode":"LB64","version":"2.1.1","appVersion":"8.0.79","action":"swp.li.user.battery.list",
 "cityCode":"010","token":"...","ticket":"...","chaosChangeBattery":true}
// 响应
{"code":0,"msg":"成功","data":[{"batteryNo":"8900000001","batteryTypeInfo":"T63L/60V45AH",
  "subscriptionStatus":0,"showSubscribeButton":false,"iconUrl":"https://m.hellobike.com/2ab0846a34.jpeg"}]}
```

### 3.2 `swp.li.user.battery.last` — 拿电量（**轮询首选，响应最小**）

```json
// 请求
{"systemCode":"LB64","version":"2.1.1","appVersion":"8.0.79","action":"swp.li.user.battery.last",
 "waitBatteryLifeCmdResultFlag":true,"cityCode":"010","batteries":[{"batteryNo":"8900000001"}],
 "token":"...","ticket":"...","chaosChangeBattery":true}
// 响应
{"code":0,"msg":"成功","data":[{"batteryNo":"8900000001","batteryLife":76,"level":1,
  "reportTime":1700000000000,"reasonCode":0,"reasonCodeText":"成功","chargeStatus":"0"}]}
```

`waitBatteryLifeCmdResultFlag:true` = 请服务端下发"查电量"指令给电池等结果；`reportTime` 是电池**上报时刻**。
抓包里它比请求时间早约 32 秒 —— 所以这是"最近一次上报值"，不是瞬时采样。**轮询间隔给 60~120 秒就够**。

### 3.3 `swp.li.user.battery.detail` — 健康度/续航/剩余容量

```json
{"batteryNo":"8900000001","batteryType":"T63L","batteryTypeInfo":"T63L/60V45AH","level":1,
 "batteryLife":76,"batteryLifeTimestamp":1700000000000,"soh":96,"sohText":"健康",
 "volt":60,"ah":45,"current":0,"status":"1","chargeStatus":0,
 "remainCapacity":"34.20Ah","endurance":"72km","energyConsumption":"28wh/km",
 "chargeCount":"153次","totalMileages":"4318km"}
```

字段含义：

| 字段 | 含义 | 备注 |
|---|---|---|
| `batteryLife` | 电量 % | 与 `battery.last` 同源 |
| `current` | 实时电流，**单位 A（安培）** | 抓包里是 `0`（静置）；`volt × current` 即充电功率(W) |
| `volt` / `ah` | **额定**电压 / 容量（60V 45Ah） | ⚠️ 不是实时电压！实时电压看 §3.6 |
| `chargeStatus` | 充电状态 | 见下表；**last 里是字符串，detail 里是数字** |
| `remainCapacity` | 剩余容量 | 带单位字符串 `"34.20Ah"` |
| `endurance` | 预估续航 | `"72km"` |
| `chargeCount` / `totalMileages` | 循环次数 / 总里程 | `"153次"` / `"4318km"` |
| `status` | 电池状态位 | 语义未知（抓包恒为 `"1"`） |

#### chargeStatus 取值（从小程序 `pages/home` 渲染逻辑反推）

```js
"1"  === d && （充电中）
"-1" === d && （已断电）
// 其余（尤其 "0"）不渲染任何标签 → 未充电/静置
```

| 值 | 含义 | 判定充电器是否结束 |
|---|---|---|
| `"1"` | 充电中 | 否 |
| `"-1"` | **已断电**（充电器断开/掉电） | 是 |
| `"0"` | 未充电（静置，可能已拔） | 是 |

抓包里 `battery.last` 返回 `"chargeStatus":"0"`、`battery.detail` 返回 `"chargeStatus":0` ——
**类型不一致，比较前统一 `str()`**，否则 `"0" == 0` 判 false 会导致状态机错乱。

### 3.4 `swp.li.user.battery.track` — GPS 轨迹（**不是**电量曲线）

响应约 2 KB，含 `location.address`（逆地理地址）+ `tracks[]`（lng/lat/locateTime/sourceType），
大约 1 个点/5 分钟。**想画电量曲线得自己按时间累积 `batteryLife`。**

### 3.5 `swp.li.user.battery.status` — 实时电气参数（「状态」页）

小程序「我的电池 → 状态」那个页面（总电压 / 电流 / 环境 / MOS / T1-T4 / 单体电压）用的就是这个接口。
**只要一个参数 `batteryNo`**（字符串）：

```json
{"action":"swp.li.user.battery.status","batteryNo":"8900000001","token":"...","ticket":"...",
 "systemCode":"LB64","version":"2.1.1","appVersion":"8.0.79","cityCode":"010"}
```

响应（与 App 页面逐项对得上）：

```json
{"batteryNo":"8900000001",
 "voltage":"65.20",            // ← 真实总电压（detail 里的 volt:60 是额定值）
 "current":"0.0",              // ← 实时电流，单位 A
 "cellMaxVoltage":"3.298/V","cellMinVoltage":"3.291/V",
 "maxCellVoltageNo":14,"minCellVoltageNo":3,"subVoltage":4,
 "envTemperature":"27","mosTemperature":"26",
 "batteryTemperatureOne":"25","batteryTemperatureTwo":"26",
 "batteryTemperatureThree":"25","batteryTemperatureFour":"26",
 "cellVoltageList":[3.257,3.259,...,3.298]   // 20 串单体电压
}
```

踩过的坑：参数名就是 `batteryNo`，**但传 null / 空字符串会得到 `101000 参数错误: 电池编号不能为空!`**，
很容易误判成"参数名不对"。我第一次试的时候 `battery_no` 恰好被清空了，于是试了 8 个候选参数名全是失败——
教训：先把参数打印出来确认不是 None。

配套的还有：

| action | 用途 | 参数 |
|---|---|---|
| `swp.li.user.battery.param` | 「参数」页（BMS 配置） | 同 `batteryNo` |
| `swp.li.user.battery.getMosStatus` | MOS 开关状态（`mosButtonStatus:1`） | `batteryNo` |
| `swp.li.user.battery.setMosStatus` | 开/关 MOS（**写操作，别碰**） | `batteryNo` + 目标状态 |

## 4. 加密与签名（源码还原）

代码在 `mp/app-service.js`，HTTP 拦截器（module 84）注册时开了 `signature:true`，实现在紧邻模块：

```js
var l = {
  dev: {key: Utf8.parse("1234567890123456"), iv: Utf8.parse("1234567890123456")},
  pro: {key: Utf8.parse("0199bec97dfa5e0d"), iv: Utf8.parse("0199bec97dfa5e0d")}
};
l.fat = l.uat = l.pre = l.dev;

// 签名：注意是对【明文】算
var t = (new Date).getTime().toString();
var n = Math.random().toString().slice(2, 8);          // 6 位
signature = HmacSHA1("" + 明文 + t + n, "386a09ea946d46f1b4ca3b4e3df8de45").toString();

// 请求体加密
data = CryptoJS.AES.encrypt(明文, l[env].key, {iv: l[env].iv}).toString();
headers.chaos = "true";
headers["x-chaos-env"] = env + "-1.1.3-beta.1";

// 响应体解密
明文 = CryptoJS.AES.decrypt(密文, l[env].key, {iv: l[env].iv}).toString(Utf8);
```

### 4.1 请求里的两个"版本号"

每个业务请求都带 `version` 和 `appVersion` + `systemCode`，三者含义完全不同：

| 字段 | 取值 | 含义 |
|---|---|---|
| `version` | `2.1.1` | **小程序自身版本**，代码里写死 |
| `appVersion` | `8.0.79` | **微信客户端版本**（`getSystemInfo().version`），PC 微信是 `4.x` → 这就是 §9 的根因 |
| `systemCode` | `LB64` | **渠道标识**，见下 |

`systemCode` 在源码里是一张按渠道分发的枚举：

```js
{ IOSApp:"", AndroidApp:"", H5:"", Wechat:"LB64", Alipay:"" }
```

只有微信渠道有值 —— 说明这个 appid 只服务微信小程序，其它渠道留空。
服务端用它区分请求来自哪个端（路由 / 埋点 / 风控）。

**它不是凭证**。实测把 `systemCode` 删掉、改成 `TEST`、或置空，`battery.status` 依然正常返回数据：

```
删掉    code=0 msg=成功 voltage=65.20
TEST    code=0 msg=成功 voltage=65.20
空串    code=0 msg=成功 voltage=65.20
```

所以别把它当密钥用；但**自己造请求时建议照抄 `LB64`**——万一某个接口校验，或服务端按渠道做风控，保持一致最安全。

**为什么一开始误判成 ECB**：key 与 iv 都固定不变，CBC 退化成确定性的 —— 同明文必然同密文
（抓包里 699 与 704 逐字节相同）、跨请求公共前缀恒为 16 的倍数，表现与 ECB 一致。
真正的区别藏在"签名算明文不加密文"这一行，只有读到源码才能确定。

## 6. 实时电量怎么搭

```
① 取 batteryNo    swp.li.user.battery.list    （一次就够，可缓存）
② 轮询            swp.li.user.battery.detail  （60~120s，响应 ~600B，一次拿全电量+电流+电压+续航）
                  └ 失败时回退 swp.li.user.battery.last（更小，但只有电量/状态）
③ 变化才落库       batteryLife / chargeStatus 变了才写一行
④ 该推才推         低电量、充电 80/90/充满、充电结束、登录失效
```

```bash
cp session.example.json session.json      # 换成自己的 token / ticket
python evwatch/battery_watch.py ping       # 登录态体检
python evwatch/battery_watch.py once       # 看一眼当前快照
python evwatch/battery_watch.py watch --interval 90 --low 20
```

> `hb_crypto.py` 已做自动兜底：找不到 `Crypto` 时会自动把 venv 的 `site-packages` 挂进
> `sys.path`，所以 `python3 evwatch/battery_watch.py ping` 也能直接跑；真缺依赖时会打印安装命令

### 6.0 充电监控：80 / 90 / 充满 + 结束检测

状态机在 `battery_watch.py::ChargeState`（抽出来的原因：没电池也能离线跑 `sim` 验证）。

规则：

1. **里程碑**：`batteryLife` 首次 `>= 80 / 90 / 100` 各推一条；一次采样跨多档只推最高那档（不连发）。
2. **充电开始**（`chargeStatus` → `1`）：清空本次已推档位，记录起始时间，用于算"本次充了多久"。
3. **充电结束**（`1` → `0` 或 `-1`）：推一条「充电结束」，带结束时的电量和时长。
   `-1` 已断电 = 充电器真的断了；`0` 未充电 = 可能已经拔了。
4. **低电量**只在**非充电**状态提醒，避免"边充边报低电"的噪音；回到 `阈值+5%` 才复位。
5. 实际采样间隔内电量可能跳变（电池是主动上报），所以判定用"首次越过"，不用等精确等于。

```bash
# 离线验证推送时机（不发消息，纯打印）
python evwatch/battery_watch.py sim

# 真发一轮模拟（会把下面 5 条真的推到钉钉）
python evwatch/battery_watch.py sim --send

# 自定义档位
python evwatch/battery_watch.py watch --milestones 50,80,90,100 --low 25
```

#### 「预计充电时长」是前端算的，不是接口字段

翻遍 `detail` / `param` / `status`，**没有任何"预计时长"字段**——小程序是自己算的。
能拿到的原料有两块：标称容量 45Ah（`detail.ah`）、实时电流（`status.current`），
以及用户设的充电限流（`swp.li.user.battery.getMaxChgCurrent` → `{"current":20,"text":"充电限流","maxCurrent":20,"minCurrent":1}`）。

所以按同样思路估算：

```
剩余 Ah  = 45 × (100 - 电量)/100
预计时长 = 剩余 Ah ÷ 当前电流(A)
```

⚠️ 磷酸铁锂是 **CC-CV** 充电，末段恒压电流会掉下来，所以这个估算是**偏乐观**的。
文案里明确标注「按 x A 估算」，不假装是官方数字。

`sim` 的实际输出（就是会推送的文案）：

```
[ 18% 0] 【电池低电量】电池 DEMO0001 电量 18%，当前未充电（电流 0.0，60V，剩余 8.10Ah，续航 17km）
[ 80% 1] 【电池充电进度】电池 DEMO0001 已充到 80%（本次充电约 22 分钟），当前充电中（...）
[ 92% 1] 【电池充电进度】电池 DEMO0001 已充到 92%（本次充电约 27 分钟），当前充电中（...）
[100% 1] 【电池已充满】电池 DEMO0001 已充到 100%（本次充电约 30 分钟），当前充电中（...）
[100% 0] 【电池充电结束】电池 DEMO0001 充电已结束，当前电量 100%（未充电），本次充电约 31 分钟
```

其中「开始充电」这条是新增的（`--no-start-push` 可关），因为 **ETA 在刚开始充的时候最有用**：

```
【电池开始充电】电池 8900000001 当前 20%，还需约 2 小时 15 分钟充满（按 20A 估算）（…）
```

关于电流和电压：**实时值来自 `battery.status`（§3.5），不是 `detail`**。
`detail` 里的 `volt:60` 是**额定**电压，`current` 也只是同一次 BMS 上报的附带值；
真实总电压（如 65.20V）、实时电流、环境/MOS/四路温度、20 串单体电压都在 `status` 里。

单位：`current` 是 **A**，`voltage` 是 **V**，所以 `voltage × current` 就是功率
（65.20V × 5.2A ≈ 339W）。文案会给出「电流 5.2A，约 339W，65.20V，环境 27℃」。
静置时 `current=0.0`；放电时是否记负数**未验证**，代码按 `abs()` 算功率，不依赖符号。

> 顺带一个可选的"真·充满"判据：如果某次充电发现 `chargeStatus` 一直是 `1` 但 `current` 已经掉到接近 0
> （涓流），那比单看 `batteryLife == 100` 更可靠。等你充一次电，把 `battery.csv` 里的
> `soc / chargeStatus / current` 三列拉出来看就能确认这个规律，届时可以加进状态机。

### 6.1 钉钉推送（已接好）
机器人安全设置是「自定义关键词：**电池**」，所以正文里必须带这两个字，否则钉钉返回
`errcode=310000 keywords not in content`。`notify.py` 会自动兜底：正文没有关键词就补
`【电池】` 前缀。若机器人还开了「加签」，把密钥填进 `dingtalk_secret` 即可（自动拼
`timestamp` + `sign`）。

```bash
# 通道自测（会真的发一条到群里）
python evwatch/battery_watch.py notify --text "【电池】通道测试"

# 正常轮询：低于阈值推一条，回到 阈值+5% 以上才复位，避免 19→18→17 连环轰炸
python evwatch/battery_watch.py watch --interval 90 --low 20
```

推送内容样例：

```
【电池低电量】电池 8900000001 电量 18%，续航约 72km，剩余 34.20Ah（未充电）
【电池监控中断】小哈登录态已失效（code=103），需重新抓包更新 token/ticket
```

配置写在 `session.json` 的 `dingtalk_webhook`（也可用 `--dingtalk` 临时覆盖）。
登录态失效（103）只推**一次**，不会每轮刷屏。

注意：

- 每条请求都要**重新生成** timestamp / nonce / signature，不能复用。
- `token` 过期后 `code≠0`，需重新走登录（698 / 扫码），这一步必须人工。
- 频控保守：单机串行、≥60s；异常退避重试。
- 电量曲线自己攒：`batteryLife` + `reportTime` 落库就是曲线。

### 6.2 自动续期：一键登录 vs 验证码登录

**一键登录自动化 —— 不可行。** `566 weixinEasyLogin` 要的是 `wechatLoginCode`，
它是 `wx.login()` 的产物：微信客户端用「该用户微信会话 + 小程序 appid」签出的**一次性票据**（5 分钟、用一次即废）。
脚本伪造不了，服务端也没有"拿 ticket 换 code"的接口。

**验证码登录 —— 可行，且报文已经逐字节复现。** 关键点：`api.hellobike.com` 的登录接口是
**明文 JSON、无 signature/timestamp/nonce**（只有 content-type + UA + Referer），完全没有加密门槛。

```jsonc
// 690 user.account.sendCodeV2
{"action":"user.account.sendCodeV2","systemCode":"LB64","env":"pro",
 "mobile":"13800138002","ssid":"AbCdEf123456789_2025-01-01"}

// 697 user.account.weixinMobileLogin  → 返回 token / ticket / key / guid / userNewId
{"action":"user.account.weixinMobileLogin","platform":1,"env":"pro","systemCode":"LB64",
 "channel":57,"mobile":"13800138002","code":"7434","ssid":"AbCdEf123456789_2025-01-01"}
```

只剩一个真问题：**怎么拿到那条短信**。三条路，从简单到自动：

| 方式 | 做法 | 命令 |
|---|---|---|
| 手动 | 发码后手工输 4 位 | `python evwatch/login.py relogin --mobile 138...` |
| **iCloud 转发（推荐）** | iPhone 快捷指令：收到含「验证码」的短信 → 抽数字 → 存到 iCloud 的 `evwatch/` 目录 | `--code-dir "<iCloud>/evwatch"` |
| 命令取码 | 邮件、Bark、企业微信机器人等，只要命令能打印出短信内容 | `--code-cmd "curl -s http://xxx/lastcode"` |

#### iCloud 转发怎么配

```bash

```

它会创建 `~/Library/Mobile Documents/com~apple~CloudDocs/evwatch/` 并写入说明。手机端照着做：

1. 快捷指令 → 自动化 → 新建个人自动化 → 触发条件「**信息**」，包含关键词 `验证码`
2. 动作：`匹配文本`（正则 `\d{4,6}`）→ `存储文件`（iCloud Drive → `evwatch`，文件名 `code.txt`）
3. 关掉「运行前询问」

Mac 端直接：

```bash

「发码之后被改动的**最新**文件」，并比对 mtime 排除上一次的旧验证码——实测三种情况都对：

- 发码前的旧文件 → 忽略（`None`）
- 新写入的文件 → 取到 `8642`
- iCloud 未下载的 `*.icloud` 占位符 → 跳过

iCloud 同步有 3~30 秒延迟，脚本默认最多等 180 秒。若看到 `code.txt.icloud` 占位文件，
用访达打开一次 `iCloud 云盘 → evwatch` 触发下载即可。

`login.py` 已实现：`send-code` / `login` / `relogin`，验证码提取做了防误判
（短信正文常带日期时间，容易被误当成验证码；实现里优先取「验证码」关键字后面的数字，否则取最后一个独立的 4~6 位数并排除年份）。

**挂进常驻服务就能无人值守续期**：

  --relogin-mobile 13800138000 \
  --code-dir "$HOME/Library/Mobile Documents/com~apple~CloudDocs/evwatch"
```

用 `deploy/install.sh` 装常驻服务时，加 `--relogin` 即可一起带上：

```bash

```

命中 `code=103` 时自动发码 → 取码 → 换 token → 写回 `session.json` → 继续轮询；
**半小时最多试一次**，避免反复发短信把自己刷进风控。

注意事项：

注意：发码接口有频控（连续发可能升级二次验证/直接拒绝），别拿它当心跳。

⚠️ 续期频率取决于 ticket 真实寿命（见 §6.3，实测已 ≥4 小时）。即便如此，发码接口有频控，
**别把它当心跳**：确认失效了再续。

- 短信登录成功后旧 token 是否立即失效**未验证**（可能会出现小程序被顶下线）。
- 短信转发链路本身要维护（手机要在网、快捷指令别被杀）。
- **更省事的替代**：挂一个常驻 mitmproxy + 手机代理，从流量里自动截最新 `token`/`ticket` 写回
  `session.json`。不需要密码、不需要短信，代价是手机上偶尔要真的打开一次小程序。
  如果你的目标只是"别断"，这条比短信自动化更稳、更少风控。

### 6.3 登录态（token / ticket）能管多久

**结论：`token` 是不变的，会过期的是 `ticket`；而 `ticket` 的寿命远不止 1 小时——实测已连续有效 4 小时以上。**

| 字段 | 行为 |
|---|---|
| `token`（32 位 hex） | **同一账号反复登录都返回同一个值**，像账号+设备绑定的稳定标识 |
| `ticket`（`b64(uid).签名`） | **每次登录都换新**（uid 段和 32 字节签名都会变），失效后请求返回 103 |

证据链：

1. **客户端没有任何过期逻辑**。源码里 `isLogin` 只判断 `token` 非空：
   `[{key:"isLogin",get:function(){var t=this.token;return Promise.resolve(!!t)}}]`
   没有 `refreshToken` 接口、没有 `expire` 字段、没有定时刷新。登录态整个塞在
   localStorage 的 `login-info`（token/ticket/guid/mobile/openId/userNewId），重启小程序直接复用。
2. **失效信号只有一个**：`code = 103`。实测把 `token` 置零或把 `ticket` 尾字符改掉，都返回 103
   → 两个字段必须成对有效。
3. **一次短信重新登录给出了决定性证据**：
   - 登录前：`token=0f1e2d3c…`、`ticket=MTgwMDAwMDAwMQ==…`（uid `1000000003`）→ 已 103
   - 登录后：`token=0f1e2d3c…`（**一模一样**）、`ticket=MTgwMDAwMDAwMw==…`（uid `1000000004`）→ `code=0` 立刻可用

   同一个 token 配新 ticket 就活了 ⇒ **过期的是 ticket，不是 token**。
4. **ticket 寿命（这里更正过一次）**：
   - 第一张 ticket 在签发后 60 分钟失效，但**失效前 20 分钟刚被"把 token 置零 / 改坏 ticket"
     的方式试探过**（那两次都返回 103）——很可能是这些无效凭据把会话顶掉了，而不是自然到期。
   - 第二张 ticket 从签发到观察时已 **3.9 小时**，中间还有一段 **1 小时 23 分钟没有任何请求**
     的空档，依然有效。

   ⇒ 真实寿命 **≥ 4 小时**，空闲容忍 **≥ 1.4 小时**。早前"ticket 1 小时过期"的说法作废。

⚠️ 仍无法区分是哪种机制：

- **滑动过期**（每次请求续期）→ 只要轮询不停就永不过期；
- **绝对过期** → 到点必死，只是阈值远大于 1 小时。

判断方法：把轮询**停 6 小时以上**再 `ping`。还活着就是长绝对 TTL；死了则是阈值小于 6 小时，
或存在较长的空闲超时。

所以"续期"= **换一张 ticket**（token 可以一直沿用，`session.json` 里的 token 通常不用改）。

**工程含义（已按新结论修正）**：

- 续期频率远低于此前估计，**短信自动续期完全可接受**（可能一天几次，而不是 24 次）；
- `watch` 遇 103 自动降频（≥15 分钟）并推送提醒，仍然是合理策略，成本更低了；
- `python evwatch/battery_watch.py ping` 会显示"已用多少天"，直接观察真实寿命。

工程上的处理：

- 补 ticket 的成本很低：手机重开一次小程序 → 重新抓一次 566/697 → 更新 `session.json`，
  或直接 `python evwatch/login.py relogin --mobile 138...`；
- 想做到"永不断"，就挂一个常驻 mitmproxy + 手机代理，写钩子从流量里自动提取最新
  `ticket` 写回 `session.json`——但要求手机上偶尔真的打开小程序
  （`wx.login` 的 code 只能由微信客户端产生，脚本无法自发登录）；
- 空闲太久是否会被回收，目前只有"1.4 小时空档仍有效"这一个数据点，别当成保证。

## 8. 怎么让它自动跑（部署）

**结论：Mac 上用自带的 launchd，不要在 Mac 上装青龙。**

| 方案 | 适合谁 | 评价 |
|---|---|---|
| **launchd**（推荐） | 自己的 Mac | 系统自带零依赖；开机自启、崩溃自动重启、睡眠唤醒后继续 |
| `--fg` 前台 | 想先用两天看看 | 一条命令，关终端就停；包了 `caffeinate` 防睡眠 |
| **pm2** | 已装 Node / 有服务器 | 命令比 launchd 简单（`pm2 start/save/startup`），但多一层依赖，日志管理更好 |
| **青龙面板** | 一堆签到脚本 | Mac 上要装 Docker + 面板，为一个 Python 脚本杀鸡用牛刀；面板本身还多一个攻击面 |
| 云函数 / GitHub Actions | 不想留机器 | **不适合**：token 是本机抓的且会过期，境外 Action 访问国内接口不稳，最小 5 分钟间隔 |

```bash
bash deploy/install.sh                            # 安装 + 启动（只监控）
bash deploy/install.sh --relogin 13800138000      # 安装 + 自动续期（ticket 过期自动续）
bash deploy/install.sh --status                   # 看状态（是否在跑 / 是否开了续期）
bash deploy/install.sh --fg                       # 前台跑，Ctrl+C 停
bash deploy/install.sh --uninstall                # 停掉并移除
```

自动续期支持三种取码方式（互斥，优先级 cmd > file > dir）：

| 参数 | 用途 |
|---|---|
| `--code-dir PATH` | **默认**，读 iCloud 的 `evwatch/` 目录（快捷指令写那就行） |
| `--code-file PATH` | 快捷指令固定写同一个文件时用 |
| `--code-cmd "CMD"` | 从邮件/Bark/机器人接口取码，命令打印出短信内容即可 |

```bash
# 例：换成自己的目录
bash deploy/install.sh --relogin 13800138000 --code-dir ~/Documents/sms
# 换回只监控
bash deploy/install.sh
```

装完可以用 `--status` 确认「自动续期：已开启 / 未开启」。

几个实际会踩的点：

1. **必须在「终端」里执行**。WorkBuddy 的沙箱里 `launchctl bootstrap` 会被拒（`Input/output error`），
   所以脚本会写好 plist 然后提示你去终端敲一条命令。
2. **合盖会暂停**。launchd 进程在系统睡眠时冻结，醒来才继续——中间的电量变化会漏。
   要真正 7×24 就用 `--fg`（自带 `caffeinate`）或把笔记本设成不睡眠。
   主力机建议直接接受"合盖不监控"，或换一台常开的机器（NAS/小主机）跑。
3. **状态会落盘**（`.charge_state.json`）：进程重启/机器重启后不会把 80% 再推一遍。
4. 日志在 `data/logs/watch.log`，launchd 不轮转，脚本只在变化时输出，长期跑也就几十 KB。
   嫌大就 `: > logs/watch.log`。

### 8.1 后台"日志空白"的两个坑（都踩过）

**坑一：Python 输出到文件是块缓冲。** launchd 把 stdout 重定向到文件时，`print` 会攒满 4KB 才落盘，
于是进程明明在跑、日志却一直是 0 字节。已修：`main()` 里 `sys.stdout.reconfigure(line_buffering=True)`，
并加了启动横幅 + 每 10 分钟一行心跳：

```
===== 2025-01-01 12:00:00 启动 =====
解释器 : /usr/bin/python3
会话   : 2025-01-01 10:12:00（已用 0.1 天）
轮询   : 90s   低电阈值: 20.0%   里程碑: [80, 90, 100]
推送   : 钉钉   续期: 开启 138****8000
12:00:01  8900000001  76%  未充电  电流 0.0A / 65.20V
12:10:01  · 心跳  soc=76%  未充电  （已 10 分钟无变化）
```

**坑二：launchd 进程不继承 shell 的代理环境，Python 也不读 macOS 系统代理。**
这台机器出网依赖本地代理（`scutil --proxy` 显示 127.0.0.1:9090，Clash TUN 用 198.18.x.x 假 IP），
所以后台服务直连时报 `SSL: CERTIFICATE_VERIFY_FAILED`，**一条请求都发不出去**——这才是"啥日志都没有"的真凶。

已加 `evwatch/net.py`：按「环境变量 → 系统代理 → 7890/1087/6152/9090 → 直连」顺序自动探测，
第一个通的缓存复用；连接层失败才换下一个，HTTP 错误不重试（避免把发短信的 POST 重放两次）。

⚠️ 还有个未解之谜：**在 launchd 上下文里所有出口的 TLS 校验都失败**（同一份代码、同一个解释器，
在普通 shell 里用 7890 或直连都能验过）。所以最后加了一档"不校验 TLS"的兜底，日志里会明确写：

```
[net] ⚠️ 所有出口的证书都验不过，已降级为不校验 TLS（设 EVWATCH_TLS_STRICT=1 可禁止）
```

**安全影响评估**：业务报文本身是 AES 加密 + HmacSHA1 签名（签名密钥在小程序里，中间人没有），
所以 MITM 既读不到明文（`token`/`ticket` 在加密体里），也伪造不出合法请求；它能做的是丢掉或重放。
可接受，但如果在意：用 `bash deploy/install.sh --fg` 在「终端」里前台跑——那个上下文 TLS 是能验过的。

```bash
bash deploy/install.sh --status      # 现在会顺带打印最近 5 行日志，肉眼确认在跑
```

### 8.2 轮询间隔该设多少（有实测数据）

当前默认 **90 秒**（`--interval 90`）。但真正的瓶颈不是轮询，而是**电池自己的上报频率**：

对 `battery.csv` 里 49 条样本（161 分钟）做统计，电池实际上报只有 **7 次**，
间隔分别是 `23.0′ / 56.2′ / 38.2′ / 1.0′ / 22.7′ / 22.5′` —— **静置时典型 22~23 分钟一次**。

也就是说 90 秒轮询里，大约 15 次请求拿到的是同一份数据（`reportTime` 一模一样）。

| 场景 | 建议间隔 | 理由 |
|---|---|---|
| 平时挂着 | **300s（5 分钟）** | 电池 22 分钟才报一次，再快也是空转 |
| 充电时 | **120~180s** | 充电时上报可能变密（待验证），快一点能更早发现 80/90 |
| 想极省请求 | 600s | 仍能保证在满电前抓到 100% |

```bash
bash deploy/install.sh --interval 180      # 改完需要手动重载（脚本会提示命令）
```

#### 小程序那个"刷新"到底是啥

翻遍 action 列表**没有独立的 refresh 接口**。小程序的"刷新"就是这个：

```js
// 源码 getBindBatteryDetail
{action:"swp.li.user.battery.last", waitBatteryLifeCmdResultFlag:true}   // showToast:false
```

`waitBatteryLifeCmdResultFlag` = 请服务端给电池**下发一条查询指令并等结果**。实测：

- 0.2 秒就返回（真等电池应答不可能这么快）
- 紧接着调 `battery.detail`，`batteryLifeTimestamp` 与它**完全一致**（都滞后 19 分钟）

⇒ **电池休眠时不会应答，服务端直接给缓存**。刷不刷新取决于电池那头醒没醒，不取决于我们请求多快。

这也印证了「有输入输出时上报更密」的判断：CSV 里唯一一次 1 分钟间隔，出现在密集请求、电池被"叫醒"的时段；其余静置时段都是 22 分钟一次。

#### 所以改成了自适应轮询

| 状态 | 间隔 | 判据 |
|---|---|---|
| 静默 | `--interval`（默认 90s） | `chargeStatus != 1` 且 `|current| ≤ 0.05A` |
| 活跃 | `--interval-active`（默认 interval/3，最小 30s） | 充电中 或 有电流 |

充电/放电时电池本来就醒着、上报密，这时候加密轮询才有意义；静置时自动降回低频省请求。
日志里切换时会打一行：

```
12:00:00  · 轮询切换为活跃模式（30s）
```

`--no-force` 可以关掉每次的主动查询（省一半请求，代价是可能更晚发现新值）。

⚠️ **预期管理**：不管轮询多快，**电量最多滞后 ~22 分钟**（因为它是电池主动上报，不是实时采样）。
`reportTime` 字段就是那份数据的时间戳，判断"数据有多新"看它而不是看本地时间。

> 换成服务器/NAS 的话：`docker run --restart=always` 挂载项目目录跑 `python evwatch/battery_watch.py watch` 即可，
> 这时用 pm2 或青龙都行——但要先解决"token 过期后怎么补"的问题（见 6.2）。

## 9. PC 端为什么提示「版本过低，请升级最新版本」

**根因：请求里的 `appVersion` 取的是「微信客户端版本」，不是小程序版本。** 源码实证：

```js
// module 29：version 直接来自 getSystemInfo
this.version = null != o ? o : "1.0.0";          // o = getSystemInfo().version

// 业务请求拼装
data: {systemCode: "LB64", version: w.b.version /*2.1.1 小程序版本*/, appVersion: g.b.version /*微信版本*/, ...}
```

抓包里每一条业务请求都是 `"version":"2.1.1","appVersion":"8.0.79"`——
`2.1.1` 是小程序版本（代码里写死），`8.0.79` 是**手机微信版本**。

而 PC 微信的版本号是另一套体系（3.9.x / 4.0.x），`getSystemInfo().version` 拿到的就是
`4.0.x` 这种值。于是同一条接口，PC 发过去就变成 `appVersion: "4.0.x"`，**版本号看起来比手机低了一个大版本**。

现象也吻合：页面一直转圈（数据请求被拒），提示文案来自**服务端下发**而不是本地代码——
反编译的主包里根本没有「版本过低，请升级最新版本」这句（只有一处未使用的错误码文案
`101:"当前版本过低，不提供服务"`）。

**已验证 / 未验证**：

| 结论 | 状态 |
|---|---|
| `appVersion` = 微信客户端版本 | ✅ 源码实证 |
| PC 微信版本号远低于手机（4.x vs 8.x） | ✅ 常识 + 现象吻合 |
| LBS 网关不校验 appVersion | ✅ 实测 8.0.79 / 4.0.3 / 3.9.12 都正常返回 |
| 电池网关按 appVersion 拦截 | ⚠️ **未证实**：鉴权在前（过期 token 一律先返回 103），无法单独测 |

**想实锤**：在 PC 上用 Proxyman/Charles 抓一次，把那条 `switchpowerapi` 响应丢进
`python evwatch/dump_all.py` 解密，看 `msg` 字段是不是这句文案——是的话就是服务端拦截，没有疑问。

对我们的方案**没有影响**：脚本里的 `appVersion` 固定写 `8.0.79`、UA 伪装手机微信，
所以手机能跑的接口脚本一样能跑。PC 端本来就只是个"顺带看看"的入口。

### 9.1 顺带查了：PC 微信把小程序登录态存在哪

```
applet/local/<appid>/usrmmkvstorage0/<appid>      ← MMKV，localStorage 就在这
applet/local/<appid>/usrmmkvstorage1/<appid>
applet/local/<appid>/mmkvadapterstorage/<appid>
```

如果 PC 端能跑起来，`login-info`（token/ticket）就会落在这里，**直接读文件就能拿到最新 token，
连代理都不需要**——这本来是理想的"无感刷新"方案。

**但实测这三个 MMKV 全是空的**（16KB 初始态，`strings` 里搜不到 `login-info`），
说明 PC 端是在**登录之前**就被拦下的 → 不是业务接口按 `appVersion` 校验（登录接口压根不传 `appVersion`），
而是**框架级/小程序发布配置的最低基础库版本限制**。

结论：改缓存包里的 JS（比如把 `appVersion` 写死 8.0.79）**绕不过去**，因为拦点在微信客户端那边。
PC 这条路可以放弃了。

## 10. 风险与合规

- 仅限**本人账号 / 本人电池**；批量拉他人电池数据属违法。
- `token` / `ticket` 等同密码；抓包里还有手机号、unionid 与实时 GPS 位置 → 脱敏后再留档，别进 git。
- 逆向仅用于接口对接研究，别去碰权益/估值/支付类接口。
- 轮询频率过高会触发风控导致 token 失效，别贪快。

## 11. 附：中国铁塔充电桩（另一套系统，用于「电池停了就结束桩」）

> 这一节跟哈啰的协议无关，但业务上紧紧依赖哈啰的电池数据。场景：电池插在**中国铁塔**的
> 交流慢充桩上充电，**电费按度 + 服务费按小时（且随功率档阶梯）**。桩自己的「充满自停」
> 判得很晚 —— 电池 BMS 已经报「不在充电」，桩还在继续计时**吃服务费**（用户实测多吃近一小时）。
> 所以要盯**电池端**，一停就调接口把桩侧订单结束。实现在 `evwatch/tower.py`。
>
> 收费模型、判据推导、参数速查、实盘时间线 → **[铁塔-充电策略.md](铁塔-充电策略.md)**。

### 11.1 跟哈啰的差别：这套是明文的

| 项目 | 哈啰小哈智电 | 中国铁塔充电 |
|---|---|---|
| 域名 | `api` / `switchpowerapi.hellobike.com` | `charge-api.chinatowercom.cn:18443` |
| 报文 | AES-128-CBC + HmacSHA1 签名 | **明文 JSON，无签名** |
| 鉴权 | 自定义 header（token / ticket / signature / timestamp / nonce） | `Authorization: Bearer <JWT>` + `deviceId` |
| 登录态 | ticket 约 4 小时+，需要续期 | JWT `exp` 约半年，但**单会话**，手机再进小程序就失效 |
| 小程序 | `wx9d7f582059211357` v12 | `wxf295d9e03b73e077` v84 |

这套不需要逆向加解密，只要拿到 header 就能构造请求。客户端逻辑（下面 §11.6、§11.7）是用
[wx-mp-mcp](https://github.com/WhiteNightShadow/wx-mp-mcp) 的 `scripts/wxapkg-decrypt.mjs`
把本机缓存的 6 个分包（`__APP__` + `_pages_siteOrder_` 等）解成 JS 后读出来的。

### 11.2 请求头

```
POST /charge/core/toc/charging/list HTTP/1.1
Host: charge-api.chinatowercom.cn:18443
content-type: application/json;charset=UTF-8
deviceId: <6 位随机小写字母，客户端生成>
Authorization: Bearer <JWT>
platform: wechat
User-Agent: <手机微信 UA>
Referer: https://servicewechat.com/wxf295d9e03b73e077/84/page-frame.html
```

`deviceId` 服务端不校验含义，照抄抓包值即可。响应偶尔带 `Content-Encoding: gzip`
（还可能是 chunked），标准 HTTP 库会自动处理。

### 11.3 用到的接口

| 路径 | 请求体 | 作用 |
|---|---|---|
| `/charge/core/toc/charging/list` | `{}` | **进行中的充电（轮询首选，约 570B）** |
| `/charge/core/toc/charging/detail/by/plugNum` | `{"plugNum":"HBLF2000000x"}` | 同一份数据，按插口查（**客户端就用它，60 秒一次**） |
| `/charge/primary/toc/order/query/charging/list` | `{"cardUid":""}` | 订单视角（`startTime` / `endTime` 是字符串时间） |
| `/charge/core/toc/charge/endCharge` | `{"plugId":25369xx,"orderNum":"CDC...","openDoor":1}` | **结束充电** |
| `/charge/primary/toc/order/query/detail` | `{"state":"1","orderNum":"CDC...","costAllMoney":0,"rid":null}` | 订单结算详情 |
| `/charge/bridge/toc/charge/scanQrCode` | `{"plugNum":"HBLF2000000x"}` | 扫码：拿到 `plugId`、余额、费率模板 |
| `/charge/core/toc/prepaid/money/details` | `{"stationId":180241}` | 站点计费配置：`fullStopMoney` / `startChargingMoney` / `switchStatus` |
| `/charge/bridge/toc/charge/start` | 见 §11.6 | 开始充电（客户端 siteOrder 页走 bridge 网关） |

### 11.4 `charging/list` 的 `resData` 字段

```json
{"resData":{
  "startTime":1700000000000,"rid":1000000007,"recordType":1,"recordState":null,"endType":null,
  "orderNum":"CDC2026102212139xxxxx","plugNum":"HBLF2000000x","plugId":25369xx,
  "chargeType":5,"power":0.0,"paymentMethod":0,"paymentMoney":1.00,"templateType":5,
  "currentTime":1700000001000,"stationName":"某站点","costMoney":0,
  "chargingTimeTotal":0,"chargingDegree":0,"voltage":220.0,"current":0.00,"payType":2,
  "occupancyFee":null,"feeType":null
},"isReadCurrent":false,"isDisplayDegree":false}
```

| 字段 | 说明 |
|---|---|
| `current` | 桩侧电流（A）。`isReadCurrent=false` 时它是 **`power/220` 换算值**，不是独立测量；客户端也会隐藏「实时电流」那一行 |
| `voltage` | 交流桩固定 220.0 |
| `power` | 功率，**单位 W**，**这才是桩实测的量**（小程序「实时功率」直接渲染它，实测 1.192kW ↔ 返回 1192.4）。`current` 反而由它换算 |
| `chargingDegree` | 已充入电量（度）。`isDisplayDegree=false` 时**恒为 0**，没有意义 |
| `chargingTimeTotal` | 已充时长，**单位分钟**（客户端「已充时长」直接渲染它，单位写死「分钟」） |
| `costMoney` / `paymentMoney` | 已扣 / 预付金额（充满自停会按站点 `fullStopMoney` 预扣，实测 60.5 元，多退少补） |
| `chargeType` | **0 = 充满自停；5 = 按时长**（客户端 siteOrder 页的按钮决定） |
| `endType` | `0` 到时自动结束；`2` 人工或接口结束（`endCharge` 之后就是这个） |
| `isReadCurrent` | **在 `data` 层**，不在 `resData` 里。`false` = 桩不上报「实时电流」，客户端隐藏该行（「实时功率」仍显示，因为它来自 `power`） |
| `isDisplayDegree` | 同上。`false` = 桩没上报度数，客户端会隐藏「已充电量」 |

没在充电时 `resData` 为 `null`（不是报错）——这也正好是「本单已结束」的判据。

> 更正：早前抓包只覆盖了「刚开充」这一瞬间，`power`/`chargingTimeTotal` 都是 0，
> 一度误以为这两个字段不可用。读客户端代码才知道前者是 W、后者是分钟，都是有效字段。

> 2026-10-23 实盘（某交流桩，`plugNum` 前缀 `DTMF`）：`isReadCurrent=false`、
> `isDisplayDegree=false`、`chargingDegree` 恒 0、`current` 稳定 5.42A。
> **但 `power` 是实测**：同一时刻小程序显示「1.192KW 实时功率」，接口返回 `power=1192.4`，
> 且 `power / 220 = 5.42` 正好等于 `current` —— 所以是「功率为主、电流换算」，
> 客户端才隐藏「实时电流」而保留「实时功率」。电池端 66.98V × 16.99A ≈ 1.14kW 与之自洽。

### 11.5 `endCharge` 的返回与确认

```json
{"code":200,"msg":"请求成功","data":{"costMoney":0,"endTime":1700000005000,"returnFlag":false}}
```

`returnFlag:false` **不代表失败**（抓包里就是这样，随后订单详情已经 `state=1`、`endType=2`）。
可靠的确认方式是回头再拉一次 `charging/list`：`resData` 变成 `null` 或换了 `orderNum` 才算真停。

`openDoor` 来自客户端 `stopCharging(t)`：`1` = 话术「仓门已打开，请取出电池」；
`0` = 跳到等待取件页、不开门。抓包里发的是 `1`。

### 11.6 客户端本来就有「充满自停」，但别指望它

siteOrder 页的时长选项是写死的：

```js
list: [1, 2, 3, "充满自停", 10, 20]      // 小时
fullStopMoney: 5, startChargingMoney: 5  // 站点配置下发后覆盖
```

点「充满自停」时（`doClick`）设 `chargeType = 0`、`selectFullStop = true`，
非微信支付分支还会把 `selectTime = 0`；然后开充报文长这样：

```js
{plugId, time: selectTime, unit: "h", sourceType: 1,
 paymentMethod, payType, payMoney,   // payMoney = fullStopMoney（预扣，多退少补）
 chargeType,                          // 0=充满自停, 5=按时长
 type: (站点 type === 7 ? 2 : 1), startType: 1}
```

问题在于这个「满」是**桩侧判断**的：桩要等到它自己认定的电流阈值才停，而电池 BMS
早就报「不在充电」了 —— 这中间的时间差按小时收费，就是用户说的「很黑」。

所以 `tower.py watch` 的判据顺序是：

1. **电池端**（权威）：哈啰 `chargeStatus` 从 `1` 变 `0`/`-1` 连续 2 次；
   或 `batteryLife = 100%` 且电池侧电流 ≤ 0.2A；
2. **桩侧兜底**（电池数据拿不到 / 电池一直没报充电中）：电流跌到
   `max(0.3A, 峰值×25%)` 以下连续 2 次。

三道防误杀：开充 3 分钟内不判、必须先观测到 `chargeStatus = 1`（否则刚插上本来就是 0）、
同一份电池缓存（`reportTime` 没前进）不重复计数。

### 11.7 坑：单点登录

铁塔的 JWT **同一时间只允许一个会话**。手机上再打开一次小程序，手上这份立刻作废：

```json
{"code":303,"msg":"账号已在其他设备登录,请重新登录"}
```

`exp` 还有半年也没用 —— 303 说的不是过期，是被挤下线。所以顺序必须是：
插枪 → 扫码开充 → 抓一次 `Authorization` → 写进 `tower_session.json` → 跑 `watch`，
**跑的过程中不要开小程序**。`status` 会先把 `exp` 剩余天数打出来，方便区分「过期」和「被挤」。

### 11.8 短信登录（自己换 token，不用再抓包）

抓包 `[611]` → `[623]` 就是完整的短信登录（`[543]` 是微信一键登录，要 `wx.login` 的 code，脚本做不了）。

**① 发码** `POST /auth/mobile/user/getValidateCode`

```json
{"cellphone":"13800138000","vailType":1,"timestamp":1700000000000,
 "sign":"1dce0b2d367733d146fe28d91effbbf1"}
```

`sign = md5( md5(手机号) + 毫秒时间戳 )`，两处都是小写 hex —— 用抓包的真实号码+时间戳复算，
结果与抓包 **逐字符一致**。返回 `{"code":200,"data":{"message":"给…发送短信成功.","ret":0}}`。

**② 登录** `POST /auth/mobile/user/login`

```json
{"cellphone":"<RSA>","code":"4651","loginType":1,"type":1,
 "miniProgramOpenId":"<微信 openid>","invitationCode":"",
 "appId":"<RSA>","coordinateY":116.3975,"coordinateX":39.9087}
```

- `cellphone` 与 `appId`（明文是 `applet_manage:123456`）都是 **JSEncrypt 加密**：
  1024 bit / PKCS#1 v1.5 / 输出 base64（172 字符）。公钥是写死的常量 `PUBLIC_KEY_KEY`。
- `coordinateY` = 经度、`coordinateX` = 纬度（客户端字段名就是反的，别对调）。
- `miniProgramOpenId` 只能从抓包里取（同一用户同一小程序恒定），登录一次后存进
  `tower_session.json` 的 `open_id`，以后复用。

响应关键字段：

```
data.tokenMap.access_token      ← Bearer JWT（我们真正要的，exp 约半年）
data.userDtoCache.token         ← 32 位 hex 老系统 token（给 exchangeOldToken 用，脚本不需要）
data.userDtoCache.deviceId      ← 本次会话的 deviceId，后续请求头要与之一致
```

**③ 换发老 token**（可选）`POST /auth/mobile/user/exchangeOldToken`
`{"uid":1000000006,"token":"<32hex>"}`，带新 JWT 的 Authorization —— 客户端登录后顺手调，
脚本不调也能正常用。

### 11.9 会话键 = token + deviceId（实测，容易踩）

同一个 JWT，只换请求头里的 `deviceId` 就 303：

| deviceId | 结果 |
|---|---|
| 登录时服务端返回的那个（`abc123`） | `code=200 请求成功` |
| 别的抓包里的（`def456`）/ 空 / 不传 | `code=303 账号已在其他设备登录` |

也就是说**登录态不是单纯挂在 token 上，而是挂在 (token, deviceId) 这一对上**。
推论：

- 从抓包导入 token 时，必须连同那一份的 `deviceId` 一起导入（脚本读的是同一个请求头）；
- 用短信登录拿到的 token，服务端会在响应里**重新发一个 deviceId**（`userDtoCache.deviceId`），
  后续请求必须用这个新的；
- iPhone 上只复制 `Authorization` 会踩坑 —— 用 Proxyman「Copy as cURL」整段存，
  脚本会把 `deviceId` 一起解析并热替换。

实现见 `evwatch/tower_login.py`（`use-capture` / `token-inbox` / `send-code` / `login` / `relogin` /
`whoami` / `icloud-setup`），取验证码直接复用哈啰那套「手输 / 文件 / 目录（iCloud 转发）/ 命令」。

**文件名固定**（iCloud 目录里还有说明文件和 token 文件，随手起名会互相干扰）：

| 用途 | 文件名 | 说明 |
|---|---|---|
| 验证码 | `verify_code.txt` | 快捷指令「存储文件」时照填，打开「覆盖」；脚本优先读它 |
| 铁塔 token | `tower_token.txt` | 内容用「Copy as cURL」整段，token + deviceId 一起存 |

没有 `verify_code.txt` 时才退回「扫目录里最新的文件」，并跳过 `tower_token.txt` 与 `说明*.md`
（否则会把 JWT 里的数字串当验证码）。

**登录态策略：抓包优先，短信兜底。** JWT `exp` 约半年，一份抓包能用很久；真正的失效信号是
被别处登录挤下线（303），而不是过期。所以：

1. `use-capture`：从最近一份 `charge-api` 请求里抠 `Authorization` + `deviceId`，
   **先调 getUserInfo 验证、通过才写入**（失效的抓包不会覆盖还活着的登录态）；
2. `relogin`：短信登录，验证码默认从 iCloud 转发目录取；
3. `watch`：遇 303 自动走第 2 步（半小时最多一次），取不到码就只告警。
