## 0. 结论

**这个后端一点加密都没有。** 明文 `application/x-www-form-urlencoded`，`token` 直接放在表单里，
响应就是 `application/json`。对比哈啰那套（AES-128-CBC + HmacSHA1 签名 + 加密响应），工作量差一个数量级。

所以本项目的第二个数据源 `evwatch/pile.py` 只有 300 行：3 个函数 + 1 张字典表 + 1 个状态机。

## 2. 认证：只有一种 token，7 天有效期

所有业务接口都靠 `token` 识别用户，放在**表单体**里（不是 Header）：

```
POST /app/business/getPersonalInfo
content-type: application/x-www-form-urlencoded

token=<TOKEN>&pageSize=20&pageNum=1
```

响应里带 `"tokenState": 200` 表示 token 有效；本项目判定失效 = `tokenState != 200` 或 `code != 0`。

### 2.1 只有一个 token（此处更正两次误判）

关于这个 token 我错了两次，都记在这：

1. 先说它是「不透明串、解不开、有效期未知」—— 错。它是标准 JWT，`base64` 解第二段就能看到 payload。
2. 又说抓包里存在「两种长相」的 token —— 也错。用脚本把 32 个文件按字节扫一遍：
   **全文只有一个 token，143 字符，出现 10 次**。之前记的 `eyW9iAHv...` 那种写法在原始文件里不存在
   （复制/查看时失真），以本条为准。

唯一事实：

```
header  {"typ":"JWT","alg":"HS256"}
payload {"phoneNumber":"138...","exp":1793352050}
exp     = 签发 + 604800 秒 = 7 天
```

**结论：一个 JWT，7 天，不是永久。** `pile.jwt_payload()` 一行就能验，不用猜。

### 2.2 失效时服务端怎么回

用签名非法的 JWT 实测（exp 正常，签名错）：

```json
{"code":0,"msg":"success","tokenState":201,"total":0,"rows":[]}
```

注意这里是 **`code=0` 但 `tokenState=201`** —— 只看 `code` 会以为成功。所以 `pile._post()`
必须同时检查 `tokenState`，本项目的判定是「`tokenState != 200` 即失效」。

```bash
$ .venv/bin/python evwatch/pile_watch.py ping
token: 2026-10-30 17:20 到期，还剩 6.98 天
```

### 2.3 那为什么用起来像「永不过期」？

因为小程序每次冷启动都会重打一次 `checkPhoneNumber`，拿本地存的手机号**换一个新的 7 天 token**，
旧的直接作废。用户全程看不到登录页，所以感觉一直是登录态。

服务端是否**严格**校验 `exp`，目前无法验证 —— 伪造一个过期但签名有效的 token 需要 HS256 密钥。
只能等到 10-30 观察：`ping` 如果那天之后还返回 `tokenState: 200`，说明它不校验 exp；
如果报失效，说明校验严格。两种情况本工具都能应付（见 §9）。

### 2.4 登录：就用 `checkPhoneNumber` 手机号直换

小程序里可能有短信验证码登录，但**抓包里始终没有** `sendCode` / `login` 这类接口 ——
登录走的是 `checkPhoneNumber`（手机号 → token），没有验证码环节。

所以本项目不做短信链路，直接用这条：`login` 一条命令换一份新 token，见 §2.5。
真要更严谨的登录（验证码 / 微信授权），得平台自己改，不是客户端能补的。

### 2.5 续期：现在能自动了（2026-10-23 18:10 抓包后）

之前只能 7 天手抓一次，因为抓包里没有登录链路。18:10 这版抓包补上了 —— **`checkPhoneNumber`
就是登录接口**，它直接返回一份新 token：

```
GET /app/business/checkPhoneNumber?phoneNumber=138...
→ {"code":0,"data":{"muser":{...},"token":"eyJ0eXAi..."}}
```

所以现在有三种续期方式，按推荐排序：

| 方式 | 命令 | 说明 |
|---|---|---|
| 自动 | `session.json` 里配 `"mobile"` | token 失效时自动重登，日志里一行「已用手机号自动续期」 |
| 手动 | `pile_watch.py login` | 立刻换一份新的 7 天 token，写回 pile.json |
| 兜底 | `pile_watch.py settoken "<token>"` | 从抓包复制，仍保留 |

**手机号全项目只存一处**：`session.json` 的 `mobile`（电池监控本来就要填）。`pile.json`
不写手机号 —— 两个文件各存一份，改一个忘一个，而且充电桩配置没必要再带一份身份信息。
临时要用别的号码就加 `--phone`，只对当次生效，不落盘。

```bash
$ python3 evwatch/pile_watch.py login
用 session.json 的 mobile 里的手机号 138****8000
登录中…
已写入 pile.json
token: 2026-10-30 18:16 到期，还剩 7.00 天
```

> ⚠️ 这条接口**没有验证码**（§7 P0 原样保留）。本工具只在全局配置里有手机号
> 时才会调它，且只能换你自己号码的 token。这是平台缺陷，不是我们该依赖的「特性」。

## 4. 字段：一单长什么样

`getPersonalInfo.rows[i]`（列表，字段少）：

```json
{
  "orderId": "20261023XXXXXXXXXXXXXXXXXXXXXXXX",
  "totalPrice": 1.00, "realPrice": 0.00, "payTime": "2026-10-23 16:45:16",
  "endType": "0c", "usedTime": 720.00, "usedElectric": 0.00,
  "status": 1, "priceType": 24, "communicationType": 0
}
```

`orderDetail.data.order`（详情，字段多）：

```json
{
  "orderId": "...", "deviceId": "0119070000XX00", "unitId": "0119070000XX02",
  "totalPrice": 1.00, "realPrice": 0.00, "paid": "1", "payType": "1",
  "payTime": "2026-10-23 16:45:16", "startTime": "2026-10-23 16:45:22",
  "endTime": "2026-10-23 16:46:22", "endType": "没接负载",
  "usedTime": 720.00, "usedElectric": 0.00, "refundStatus": 0, "status": 1
}
```

**订单号是有规律的**：`<下单时间 YYYYMMDDHHMMSS>` + `<年>` + `<unitId>`。
（形如 `20261023164516` + `2026` + `0119070000XX02`；这里只保留结构，真实值已脱敏。）
`unitId = deviceId + 桩号`。也就是说 `orderDetail` 不带 token + 订单号可推导 —— 见 §7 P1。

`device` 段里还有：网点（`deptName`/`communityName`）、地址、运维真名（`sellerName`）、
`deviceUnits`（插座数）、`minUsetime`、`basicRatio`。本项目只用 `deviceName`/`deviceAddress`。

### 4.1 结束原因字典（28 条，直接抄进代码）

| 代码 | 含义 | 代码 | 含义 |
|---|---|---|---|
| `00` | 充电中 | `0c` | **没接负载** |
| `01` | 超过最大功率上限 | `0d` | 失败订单 |
| `ee` | 扫描结束 | `0e`/`05` | 充电时长用完 |
| `ff` | 异常订单 | `15`/`06`/`30`/`31` | 充满自停 |
| `40` | 远程停止 | `16` | 已达到充电时长上限 |
| `02` | 充电器过热断电/拔插头 | `20` | 紧急开关打开 |
| `03` | 停电 | `21` | 桩接地异常 |
| `04` | 金额用完 | `22` | 充电枪连接异常 |
| `07` | 电量用完 | `23` | 车辆 BMS 主动结束 |
| `08` | 远程跳闸 | `50` | 线路故障 |
| `09` | 主动关闭 | `51` | 箱门打开，请联系管理人员 |
| `0a` | 过压跳闸 | `0b` | 功率变化 |

其中 13 条属于**故障**（`BAD_ENDS`），推送时单独换标题，不和「充满自停」混在一起。

## 5. 计费模型（product 24515「深圳电价分离」）

```
总价 = 电费 × 度数  +  服务费 × 度数
```

| 项 | 非会员 | 会员 |
|---|---|---|
| 电费 | 1.108 元/度 | 0.880 元/度 |
| 服务费 0–150W | 0.34 元/度 | 0.10 |
| 服务费 151–300W | 0.45 元/度 | 0.10 |
| 服务费 301–450W | 0.58 元/度 | 0.10 |
| 服务费 451–600W | 0.70 元/度 | 0.10 |

- 综合最低价：非会员 **1.448 元/度**，会员 **1.208 元/度**
- **功率越高越贵**（服务费 0.34 → 0.70，翻倍），这是惩罚大功率车的设计
- `getPushOrder.region` 就是"你现在落在哪一档"，例如 `"0-150W"`
- 其它：`minBalance: 10`（最低充值/余额门槛）、`prepayPrice: 0.5`、`chargeUnit: 1`

> 单价是从 `orderProduct.morerangePrice`（一个嵌套 JSON 字符串）里解的，
> `pile.price_hint()` 会按当前 `region` 挑对应档位的服务费拼成人话。

## 6. 怎么判定"在充电"

充电桩接口**不给你电池 SOC**，所以判据只能是功率和订单状态。三个信号按可靠性排序：

| 信号 | 可靠度 | 说明 |
|---|---|---|
| `endType == "00"` | ★★★ | 字典里 `00` 就是「充电中」，列表接口每行都带 |
| `endTime` 为空 | ★★ | 只有 `orderDetail` 有，列表接口不返回 |
| `status == "0"` | ★ | 实测结束单为 `1`，但语义未完全确认 |

`pile._is_active()` 按这个顺序判，别只用 `endTime` —— 列表接口里它永远是空的，
只用它会把**已结束的单误判成充电中**（这个 bug 在第一次跑 `ping` 时就现形了）。

### 6.1 状态机与推送

`PileState` 只有四个触发点：

| 触发 | 条件 | 文案头 |
|---|---|---|
| 开始充电 | 上一轮非充电 → 本轮充电中 | `【电池充电桩】开始充电` |
| **计费了但没充上电** | 充电中 且 `power ≤ 0` 持续 ≥ 180s | `【电池充电桩】已计费但没充上电` |
| 充电结束 | 充电中 → 已结束 | `【电池充电桩】充电结束` / `…充电异常结束` |
| 钱可能白花 | 结束 且 `totalPrice > 0` 且 `usedElectric ≤ 0` 且 `refundStatus == 0` | `【电池充电桩】钱可能白花` |

第 2、4 条就是 2026-10-23 那单 ¥1 的教训：**付了钱、1 分钟就"没接负载"结束、0 度电、退款状态 0**。
这类静默失败如果不推，人根本不会发现。

推送走 `notify.push()`，和电池监控共用钉钉/企业微信通道；正文都含「电池」，
钉钉机器人的「自定义关键词：电池」能过。

---

### 6.2 只监听 + 自动停（不做开始充电）

**开始充电不做了。** 不是偷懒：这条路最后一步是微信支付分确认
（`wx.requestPayment`，要输支付密码），只能在手机小程序里点，脚本到预下单就得停。
所以本项目只做「监听 + 结束」。

**判满靠三档，从硬到软：**

| 判据 | 条件 | 说明 |
|---|---|---|
| 桩报充满 | `endType ∈ {06,15,30,31}`（充满自停）且订单还没关 | 最权威，但桩报得晚 |
| 功率掉下来 | 本单**见过** `power ≥ 20W`，之后掉到 `≤ 8W` 并持续 10 分钟 | 主力判据，见下 |
| 上限兜底 | `--max-hours` / `--max-money` 到点 | 防过夜 |

**为什么功率判据要加「先见过有载」这个前提**：18:08 那单全程 `power = 0`、`elf = 0`，
但不是桩不报 —— 是**当时没插车**（没接负载）。只有先看到功率上过 20W，才有资格把
「掉到 8W 以下」解释成充满/拔车；否则没插车时一上来就是 0，会被误判成立刻充满。

参数：

```bash
python3 evwatch/pile_watch.py watch \
    --interval 300 --interval-active 60 \
    --load-watts 20 --idle-watts 8 --full-minutes 10 \
    --max-hours 8 --max-money 10
```

- `--load-watts` / `--idle-watts`：有载 / 空载阈值（两轮车桩正常功率 100-200W）
- `--full-minutes`：空载持续多久算满（0 = 关掉这条判据）
- `--max-hours` / `--max-money`：硬上限（0 = 不限）
- `--no-auto-stop`：只监听，永不自动停

**进度的真话**：这台桩的 `power`/`elf`/`usedElectric` 在没负载时全是 0；
有负载时是否真的会给数，目前**只有等真充一次才能确认**。所以 CSV 里同时记
`elapsed_s`（按 `startTime` 算的真实时长）和 `totalPrice`（实测会实时累加，1.00 → 4.26），
这两个是确定可信的。

## 7. 安全发现（按严重度）

抓包顺手看到的，**不构成本项目的功能**，但如果这是自家/受测系统，这些是必修项。

### P0 · `checkPhoneNumber` 无验证码直接发 token

```
GET /app/business/checkPhoneNumber?phoneNumber=13800138000
→ {"code":0,"data":{"phoneNumber":"138...","userState":201,
     "muser":{...},"token":"ey..."}}
```

只要一个手机号，就返回该账号的完整用户对象**和可用 token**。没有短信验证码、没有 `wx.login` code 校验、
没有签名。这个 token 在后续 9 个接口里直接通行（本项目实测 `getPersonalInfo`/`orderDetail` 均 200）。

等价于：**知道手机号 = 能进别人账户**（查订单、余额、常去网点、代发起充电、远程停别人的充电）。
修法：绑定 `wx.login` 的 code → openid，或加短信验证码；至少要加频控和图形验证。

> 本项目的自动续期正是用了它（§2.5），但只喂自己的手机号。这是**明知有缺陷仍使用**的选择，
> 使用者要知道自己在依赖什么。

### P1 · `orderDetail` 无需鉴权（IDOR）

`orderDetail` 只传 `orderId`，不传 token 也返回完整订单（含设备、网点、金额）。
订单号 = 时间 + 年 + unitId，可枚举。修法：加 token 校验 + 归属校验。

### P1 · Shiro 指纹 + 若依框架

响应头固定带 `Set-Cookie: rememberMe=deleteMe`，字段风格是若依（`dictCode`/`dictLabel`/`cssClass`/`isDefault`）。
这个组合历史上是 Shiro 反序列化、druid 未授权、SQL 注入的高发面。

### P2 · token 位置不当

`checkPhoneNumber` 把手机号放 query（会进 nginx access log）；
其余接口把 token 放表单体（同样进日志）。日志泄露 = 凭证泄露。应改 `Authorization` 头。

### P2 · 过度返回

`muser` 里有 `addIp`/`lastIp`（值是 `127.0.0.1`，说明反代没传真实 IP）、`password`/`salt` 空字段；
`orderDetail.device` 里有运维真名 `sellerName`、`unionUser`、`deptId`、`deviceSerial`。
客户端用不到的字段不该下发。

## 8. 和哈啰那套的差异

| | 小哈智电（哈啰） | 麦希充（北电云） |
|---|---|---|
| 报文 | AES-128-CBC + HmacSHA1 签名 | 明文表单 |
| 响应 | 加密 JSON | 明文 JSON |
| 身份 | `token` + `ticket` 双凭证 | 单个 `token` |
| 失效信号 | `code=103` | `tokenState != 200` |
| 数据 | 电池 SOC / 电流 / 电压 / 温度 | 订单 / 实时功率 / 用电量 / 金额 |
| 登录续期 | 短信验证码（可全自动） | 只能重新抓包（本项目不实现 P0 那条路） |
| 代理 | 必须（api.hellobike.com 走代理） | 不需要（国内直连即可） |

## 9. 怎么用

```bash
# 1. 抓一次 token：手机开小程序 → 进「我的-订单」→ ProxyPin 里找 checkPhoneNumber 的响应
cp pile.example.json pile.json
#    把 data.token 填进去，obtained_at 填抓到的时间

# 2. 验证
.venv/bin/python evwatch/pile_watch.py ping
.venv/bin/python evwatch/pile_watch.py once

# 3. 离线看状态机会推什么（不联网、不发消息）
.venv/bin/python evwatch/pile_watch.py sim

# 4. 开跑
.venv/bin/python evwatch/pile_watch.py watch --interval 300 --interval-active 60

# 5. 常驻
bash deploy/install.sh --pile
```

日志：`data/logs/pile.log`；数据：`data/pile.csv`；状态：`data/.pile_state.json`。
CSV 每行一次采样，`active=1` 表示充电中，`power` 是实时功率。

## 10. 风险与合规

1. **仅限本人账号、本人订单。** 本文档里 P0/P1 是缺陷描述，不是操作指南；本项目不实现任何绕过登录的路径。
2. token 只有 7 天，本工具**不会**自动续期。到期 `ping`/日志会说清楚，重新抓包更新 `pile.json` 即可
   （`obtained_at` 换成新时间，`ping` 就能算出新的剩余天数）。
   想全自动有两条路：**短信登录**（正规，需要补一次登录链路的抓包，见 §2.3）
   或 **`checkPhoneNumber` 手机号直换**（§7 P0，本质是平台的鉴权缺陷，本项目不实现）。
3. 轮询频率别抬太高：空闲 300s、充电 60s 已经够用，`getPersonalInfo` 一秒钟打十几次没有意义且可能触发风控。
4. 接口随时可能变。变了就照 §3 的表重新对一遍字段，`pile.py` 的容错都写在 `snapshot()` 里。
